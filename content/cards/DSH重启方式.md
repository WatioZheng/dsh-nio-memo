# DSH 重启方式（通用版）

> 场景：改了 **DSH 插件 host 代码 / 服务级配置 / unit 文件**，需要让服务重启才生效时，按本卡执行。
> ⚠️ **「是否允许自行重启」由本卡自带的「权限板块」决定**（档位：禁止 / 允许；默认**禁止**＝必须先取得用户明确授权）。
> 卡面上那个带颜色的按钮显示的就是**当前档位**，点它即可切换。

## 一、什么改动需要重启

- **需要重启**：插件 host 端代码（构建进 `lib/index.js`）、服务级配置、unit 文件（改后须 `daemon-reload`）。
- **免重启**：热装载段（如模型 provider 配置）、凭证文件；纯前端改动另说（见下 §四）。

## 二、方式 A · 立即重启（会打断当前回复）

```bash
systemctl restart <服务名>        # 例：dsh.service
```

仅在明知会打断且可接受时使用。

## 三、方式 B · 延迟重启（推荐）

用**独立 cgroup 的 transient unit** 执行，脚本不会被自己的重启连坐杀掉，也不会掐断正在发送的回复：

```bash
systemd-run --unit=<前缀>-$(date +%s) --collect --no-block \
  bash -c 'sleep <延迟秒>; systemctl restart <服务名>'
```

要点：

- 延迟建议 **15~180 秒**，确保当前回复已送达。
- 若改用一次性定时单元（timer / `onceNN`），编号**必须递增、禁止复用**；取号要读**卡片 + 归档 + journal 硬证据**三处最大值 +1。
- **清理时机是「确认服务已重启、PID 已变」之后**，不是排完程就删（曾因此把排好的重启删掉、重启从未发生）。
- 每次排程后**回写编号锚点**，否则下一个人必撞号。

## 四、重启前后清单

- [ ] 已确认授权（权限卡为「禁止」时必须先问用户）
- [ ] 已记录旧 PID / 旧启动时间
- [ ] 已排程延迟重启，并回写编号锚点
- [ ] 重启会 **SIGTERM 整个 cgroup**：会话内后台任务（含各类哨、订阅进程、托管 job）会被一并杀掉且**无通知** → 重启后各自重挂
- [ ] 重启后：服务 `active`、PID 已变、邻居服务（论坛 / 工坊 / 代理等）正常
- [ ] 纯前端改动：告知用户**硬刷新**（Ctrl/Cmd+Shift+R），否则看到的仍是旧 bundle
